# Benchmark 执行规范

适用于 `benchmarks/` 下的性能测量与 profiling。仓库通用约定见 [根目录 AGENTS](../AGENTS.md)。

**运行前必须明确所有轮数、预热和重复执行次数，列出完整清单并取得用户确认。不得自行采用默认次数启动实验。**

## 实验目录与公共入口

每个具体实验目录必须提供 `README.md`，介绍实验目标、比较的问题、支持的脚本及职责、通用依赖、参数和运行方式。新用户无需已有 artifacts，也应能理解实验并运行它。

README 保持环境中立：可以列相对脚本名、仓库相对路径、通用输出位置和参数占位符；不写个人绝对路径、专属解释器或 Conda 环境、实际硬件型号、机器配置或特定 GPU 编号。具体设备选择通过参数表达。某次运行的实际命令、环境、执行次数和结论属于结果记录，不能把历史运行当成公共使用前提。

## 实测总结与原始材料

| 位置 | 维护职责 |
| --- | --- |
| 实验目录的 `README.md` | 环境中立的公共入口；链接脚本、结果索引和相关设计 |
| 实验目录的 `results/` | 纳入 Git 的完整实测总结，是实验条件与数据的权威记录 |
| 实验目录的 `artifacts/` | Git 忽略的原始 JSON、日志、trace、源码快照及自动生成的报告 |
| Design 的 proposal / current | 在对应方案或架构文档中引用实测依据，按设计生命周期维护 |

实测总结必须独立可读，保留测试日期、CPU/GPU 型号及相关硬件配置、软件版本、测量代码版本（含未提交变更的说明）、精度、模型规模、算法配置、计时口径、实际执行轮数/预热/重复次数、主要数据、正确性检查、失败或排除项及局限。结论限定于已测条件；理论分析与实测结果分开表述，不能把局部收益写成普遍性能保证。

原始 artifacts 可以仅存在于运行者本地，不要求随 Git 提供或提供可访问链接。实测总结注明原始材料的可用性，可补充实验标识、相对目录或源码哈希；缺失的历史信息标为未记录，不推测补齐。关键数据和证据范围不得只存在于本地链接指向的文件里。图表若为理解总结所必需，应纳入 Git 的 results；本地图表只能作为可选补充。

报告脚本默认在输入 artifacts 目录生成派生报告，不直接覆盖维护中的 README、Git 结果总结或 Design 摘要。显式输出路径仍可用于生成待审阅的结果材料，纳入 Git 的总结由审阅后更新。原始样本、失败记录和历史测量条件必须保留，不在整理文档时重新解释为新的测量。

Design 按设计生命周期引用实测：比较中的候选、选型依据和拟采用方向归对应 proposal；已落地方案的当前行为、限制及必要理由归 current 的架构或专题文档。直接链接 benchmark 总结，不要求建立 Design 结果目录或独立索引页，也不按实验批次在 current 新增摘要页。具体硬件与完整实验协议留在 benchmark results；引用时保留必要的适用条件，区分已实现、拟采用与尚未验证。详见 [Design 结果规范](../docs/design/AGENTS.md#reference-与结果记录)。

方案被替代后，相关 benchmark 可以停止维护、归档或在范围明确的清理中删除脚本。保留的历史结果须注明所测版本、适用范围及被替代状态；有后继方案时链接其说明。历史数据不随新实现改写，也不承诺旧脚本始终能在当前版本运行。实验关闭不等于历史结果失效，历史结果也不代表当前实现的性能。

## 按比较目的确定次数

- 粗略比较不同方法、判断较大性能差距时，只提出 **1 个独立进程轮次**，不默认做三轮复测。
- 一轮内允许多次计时，但预热次数和正式计时重复次数必须分别提出并经用户确认；“一轮”不代表允许任意次数的进程内重复。
- 只有用户明确要求细致比较差距不大的方法，或进行正式性能评估时，才提出多个独立轮次；具体轮数仍须确认。
- 脚本默认参数、历史命令及其他实验的协议，不构成本次运行授权。一次测量只能支持初步性能比较，不能据此声称跨进程稳定性。

## 运行前确认清单

先读取实际驱动，核查首次执行、内部循环及额外校验；不能只列命令行上的 `rounds`、`warmup` 和 `repeat`。按设备、配置及方法展开清单；数值完全相同的组合可以合并展示，但必须写清组合数量。

| 项目 | 必须列明的内容 |
| --- | --- |
| 工作负载 | 设备、模型规模、仿真时长、dt 和每次完整仿真的步数 |
| 比较方法 | 所有方法及基线；同一基线是否在不同候选进程中重复测量 |
| 独立轮次与进程 | 独立轮数、每轮进程数、总进程数，以及串行或并行执行方式 |
| 首次执行与预热 | 每个方法的首次编译执行次数、额外预热次数；首次执行是否已经计入预热，避免重复统计 |
| 正式计时 | 每个方法、每个进程内的计时次数，计时范围及设备同步方式 |
| 额外执行 | 轨迹校验、reset 校验、profiling、诊断或试跑引入的模型执行次数；reset 调用本身与 reset 后的完整仿真分别列出 |
| 总量 | 方法结果数、正式计时总次数、包含首次执行/预热/校验的模型执行总次数 |
| 时间与失败处理 | 预计墙钟耗时、总预算、单进程超时，以及是否包含重试；包含时列出重试范围和次数上限 |

明确区分以下计数，不笼统使用“跑一次”：

- **独立轮次**：整组配置的一次独立复测；每轮可能启动多个进程。
- **进程**：一次独立程序启动；一个进程可能测量多个方法。
- **方法结果**：一个方法在一个设备、配置、轮次和进程中的计时记录；多次计时可以汇总成一条结果。
- **完整仿真执行**：模型从指定初态或起点推进预定步数一次；首次执行、预热和校验也可能包含完整仿真。
- **仿真步**：一次 dt 推进，不等同于一次完整仿真。

例如，若某方法每进程包含一次首次执行、W 次额外预热、R 次正式计时、V 次额外完整仿真校验，则该方法每进程执行总数为 `1 + W + R + V`。若首次执行已包含在 W 中，应改用实际计数。此例仅解释计数关系，不授权任何默认次数。

## 确认后的执行与变更

1. 清单确认后才能启动对应 benchmark。通过脚本、notebook 或 pytest 触发实际性能测量，都必须遵守此规则，不能用“先试跑”绕过确认。
2. 使用显式参数落实已确认次数，并核对脚本内部执行与清单一致。现有 CLI 默认值及历史复现命令不因本规范自动改变。
3. 已确认且未变化的协议直接执行，不重复索取确认。增加设备、配置、方法、轮次、预热、计时重复或额外校验执行前，说明变化并重新确认。
4. 失败时保留日志和已完成结果。只执行清单中已确认的重试；没有授权重试时，先说明失败原因及拟重跑的范围、次数和预算，不自行重跑整套矩阵。
5. 达到确认的超时或总预算时停止并保存未完成项，不自动扩大预算或转入长期后台运行。
6. 报告记录实际执行次数及与清单的偏差。首次编译、预热、稳态计时和额外校验分别说明，不能用结果条数代替实际运行次数。

读取源码、查看已有结果、检查文档链接及不执行实际性能测量的静态检查，不需要启动 benchmark，也不需要为这些操作申请测量次数确认。
